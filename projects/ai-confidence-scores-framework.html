1. The Overconfidence Problem in Production LLMs

When deploying modern Large Language Models (LLMs) such as Gemini 2.5 Flash to automate unstructured document processing, one issue repeatedly surfaces: raw probability outputs from instruction-tuned models are severely uncalibrated. Post-training reinforcement learning (RLHF/RLAIF) aligns models to generate fluent, decisive completions, but it systematically squashes predicted token log probabilities toward 1.0 or 0.0. As a result, a raw model confidence score of 0.98 does not mean the model is right 98% of the time.

In high-stakes enterprise applications, such as candidate resume parsing and recruiter routing, uncalibrated overconfidence creates hidden failure modes. An erroneous domain classification (for instance, classifying a Financial Analyst as a Data Scientist) might pass through automated hiring workflows without triggering a human review. Conversely, setting an arbitrary fixed threshold on uncalibrated probabilities leads to either auditing too many correct extractions or letting critical errors slide.

To address this challenge, I built ai-confidence-scores, an enterprise-grade evaluation and calibration framework using Google's modern google-genai SDK. I implemented, benchmarked, and comparative-evaluated 9 distinct confidence scoring techniques across multimodal PDF resumes. My objective was to determine which calibration frameworks deliver true statistical accuracy while minimizing runtime latency and API overhead.

Official Reference Documentation: For foundational concepts on token log probabilities in Gemini, explore the official Gemini Logprobs Tutorial Notebook and the Gemini GenerationConfig API Reference.

2. The Dataset & Ingestion Pipeline

Evaluating confidence calibration requires a realistic dataset with complex, multi-page formatting and inherent domain ambiguity. For this benchmark, I used synthetic PDF candidate resumes. Synthetic resumes mirror real-world applicant data: non-standard job titles, multi-column visual layouts, mixed technical keywords, and varying experience lengths across multiple career transitions.

To ingest these documents, I built a dual parsing pipeline in src/ingestion.py that provides two complementary input paths for Gemini 2.5 Flash:

  • Layout-Preserved PyMuPDF Text Extraction: Extracts structural text blocks using pymupdf (fitz), injecting page demarcation tags (--- Page N ---) for zero-latency CPU text processing.
  • Direct Native Multimodal PDF Ingestion: Reads raw PDF bytes into types.Part.from_bytes(data=pdf_bytes, mime_type="application/pdf"). This passes raw visual document bytes straight to Gemini's vision engine, bypassing text parsing errors caused by complex multi-column grids or custom fonts.
from pathlib import Path
from typing import Tuple, Union
import pymupdf as fitz

class ResumeIngestor:
    """Handles scanning, loading, and text layout extraction for PDF resumes."""

    def __init__(self, data_directory: Union[str, Path] = "./data"):
        self.data_directory = Path(data_directory)

    @staticmethod
    def extract_text_pymupdf(pdf_path: Union[str, Path]) -> str:
        """Extract layout-preserved text from PDF using PyMuPDF."""
        extracted_text = []
        with fitz.open(pdf_path) as doc:
            for page_num, page in enumerate(doc):
                text = page.get_text("text")
                if text.strip():
                    extracted_text.append(f"--- Page {page_num + 1} ---\n{text}")
        return "\n\n".join(extracted_text).strip()

    @staticmethod
    def load_pdf_bytes(pdf_path: Union[str, Path]) -> bytes:
        """Load raw PDF bytes for native Gemini multimodal ingestion."""
        return Path(pdf_path).read_bytes()

3. Pydantic Contracts and Flexible Domain Schemas

A core design choice of this framework is strict schema enforcement. By leveraging Pydantic, all extractions are guaranteed to conform to structural contracts. The core benchmark targets ResumeExtraction, which categorizes candidates into domain roles and seniority tiers while capturing atomic factual claims for factual verification.

Handling unstructured LLM outputs requires robust enum validation. I implemented custom _missing_ classmethods on domain enums to map messy LLM string returns (such as "Machine Learning Engineer" or "AI Researcher") directly to canonical enum values (such as DomainRole.DATA_SCIENCE).

from enum import Enum
from typing import List, Optional
from pydantic import BaseModel, Field

class DomainRole(str, Enum):
    SOFTWARE_ENGINEERING = "Software Engineering"
    DATA_SCIENCE = "Data Science"
    FINANCE = "Finance"
    HUMAN_RESOURCES = "HR"
    BUSINESS_DEVELOPMENT = "Business Development"
    OTHER = "Other"

    @classmethod
    def _missing_(cls, value: object) -> "DomainRole":
        if isinstance(value, str):
            val_lower = value.lower()
            if any(k in val_lower for k in ["data", "machine learning", "ai", "analytics"]):
                return cls.DATA_SCIENCE
            if any(k in val_lower for k in ["software", "engineer", "developer"]):
                return cls.SOFTWARE_ENGINEERING
            if any(k in val_lower for k in ["finance", "accounting", "financial"]):
                return cls.FINANCE
            if any(k in val_lower for k in ["hr", "human", "recruitment", "talent"]):
                return cls.HUMAN_RESOURCES
            if any(k in val_lower for k in ["business", "sales", "marketing"]):
                return cls.BUSINESS_DEVELOPMENT
        return cls.OTHER

class ResumeExtraction(BaseModel):
    """Specialized extraction schema for PDF Resume classification benchmark."""
    candidate_name: str = Field(default="Unknown Candidate", description="Full candidate name")
    domain_role: DomainRole = Field(default=DomainRole.OTHER, description="Classified professional domain role")
    seniority_level: str = Field(default="Other", description="Extracted candidate seniority level")
    years_of_experience: float = Field(default=0.0, description="Estimated total years of professional experience")
    key_skills: List[str] = Field(default_factory=list, description="Top technical and professional skills")
    key_claims: List[str] = Field(default_factory=list, description="Atomic factual claims extracted from resume")

class CalibrationResult(BaseModel):
    engine_name: str
    extraction: ResumeExtraction
    raw_confidence: float
    calibrated_confidence: float
    audit_decision: str  # "AUTOMATE" vs "FLAG_FOR_HUMAN_REVIEW"
    latency_ms: float
    metadata: dict

4. Mathematical Breakdown & Architectural Implementation of the 9 Calibration Engines

I structured the calibration suite around 9 distinct engines, spanning token-level statistics, post-hoc statistical modeling, sampling agreement, verbalized self-assessment, and context alignment verification.

Engine 1: Native Token LogProb Engine (NativeLogProbEngine)

This engine requests token log probabilities directly from Gemini 2.5 Flash by configuring response_logprobs=True and logprobs=5 in types.GenerateContentConfig. It computes the raw joint sequence confidence as the exponentiated geometric mean of all output token log probabilities:

$$\text{Confidence}_{\text{native}} = \exp\left( \frac{1}{N} \sum_{i=1}^N \text{logprob}_i \right)$$

Engine 2: LogProb Delta Engine (LogProbDeltaEngine)

Because full sequence joint log probabilities suffer from length penalty decay and saturation, Engine 2 measures the top-token dominance margin. For each generated token, it computes the log-probability margin between the selected top token (\(\text{logprob}_{\text{top\_1}}\)) and the runner-up token (\(\text{logprob}_{\text{top\_2}}\)):

$$\Delta = \text{logprob}_{\text{top\_1}} - \text{logprob}_{\text{top\_2}}$$ $$\text{Confidence}_{\text{delta}} = \sigma(\bar{\Delta}) = \frac{1}{1 + e^{-\bar{\Delta}}}$$

If the model is certain of its choice, \(\Delta\) is large. If an alternative candidate token is close in likelihood, \(\Delta\) collapses toward 0, indicating classification hesitation.

Engine 3: Post-Hoc Temperature Scaling Engine (TemperatureScalingEngine)

Temperature scaling applies a single learned parameter \(T > 1\) to smooth output token logits \(z_i\) post-hoc, optimizing Negative Log-Likelihood (NLL) on a holdout calibration set without altering classification argmax predictions:

$$P_{\text{calibrated}}(i) = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)}$$

Engine 4: Platt Scaling Logistic Engine (PlattScalingEngine)

Platt Scaling fits a 1D logistic regression model mapping the empirical token delta \(\bar{\Delta}\) (or sequence logprob) directly to true empirical correctness on a validation fold:

$$P(y=1 \mid \bar{\Delta}) = \frac{1}{1 + \exp(A \cdot \bar{\Delta} + B)}$$

This transforms raw margin statistics into true calibrated empirical probabilities, correcting for global model overconfidence bias.

from sklearn.linear_model import LogisticRegression
import numpy as np

class PlattScalingEngine(BaseConfidenceEngine):
    """Engine 4: Platt Scaling Logistic Engine."""

    def __init__(self, **kwargs):
        super().__init__(**kwargs)
        self.platt_model = LogisticRegression()
        self.is_fitted = False

    def fit(self, val_deltas: np.ndarray, val_correctness: np.ndarray) -> None:
        """Fit 1D Logistic Regression mapping logprob deltas to empirical correctness."""
        X = val_deltas.reshape(-1, 1)
        y = val_correctness.astype(int)
        self.platt_model.fit(X, y)
        self.is_fitted = True

    def evaluate(self, input_text: str, **kwargs) -> CalibrationResult:
        # 1. Fetch response with logprobs=5
        # 2. Compute mean token delta \bar{\Delta}
        # 3. Apply fitted Platt logistic model:
        if self.is_fitted:
            calibrated_conf = self.platt_model.predict_proba(np.array([[mean_delta]]))[0, 1]
        else:
            # Unfitted default fallback sigmoid curve
            calibrated_conf = 1.0 / (1.0 + np.exp(-(1.2 * mean_delta - 0.5)))

Engine 5: Self-Consistency & Sampling Agreement Engine (SelfConsistencyEngine)

Engine 5 runs \(N=5\) stochastic completions in parallel at a higher sampling temperature (\(T=0.7\)). It clusters the structured JSON outputs by primary field matches and returns the majority cluster ratio as the confidence estimate:

$$\text{Confidence}_{\text{self-consistency}} = \frac{\text{Majority Cluster Size}}{N}$$

Engine 6: Structured Self-Assessment Engine (VerbalizedConfidenceEngine)

Engine 6 asks Gemini 2.5 Flash to evaluate its own confidence. Using Pydantic JSON schema enforcement (response_schema=VerbalizedConfidenceOutput), the prompt forces the model to generate a chain-of-thought rationale followed by a verbalized score \(S_{\text{verb}} \in [0.0, 1.0]\).

Engine 7: Continuous Numerical Prompting Engine (ContinuousPromptingEngine)

Similar to Engine 6, Engine 7 prompts the model for a continuous integer rating \(R \in [0, 100]\) alongside step-by-step reasoning, normalizing the output to a 0.0 - 1.0 scale:

$$\text{Confidence}_{\text{continuous}} = \frac{R}{100.0}$$

Engine 8: Grounding & Context Alignment Engine (GroundingAlignmentEngine)

Engine 8 verifies facts using Natural Language Inference (NLI). It parses atomic factual claims from the LLM extraction (for instance, "Candidate managed a $2M budget at Company X") and runs each claim through an NLI verification check against the raw PDF source text:

$$\text{Grounding Score} = \frac{\text{Supported Claims}}{\text{Total Extracted Claims}}$$

Engine 9: Two-Tier Evaluator Engine (LLMAsAJudgeEngine)

Engine 9 routes extractions to a secondary judge instance of gemini-2.5-flash acting as an auditor. The judge evaluates the candidate extraction against a strict rubric scoring precision, hallucination risk, and completeness on a 1–5 scale, normalizing the overall rubric average to \([0.0, 1.0]\).

5. When to Use Each Calibration Engine

Choosing the right calibration framework involves balancing runtime latency, API cost, logprob availability, and compliance requirements:

7. Production Challenges & Engineering Lessons

Building this benchmark surfaced several key technical considerations for LLM confidence calibration:

  • SDK and API Schema Nuances: In the modern google-genai SDK, token alternative log probabilities are nested inside response.candidates[0].logprobs_result.top_candidates. Ensuring fallback logic for legacy structures is essential for cross-version compatibility.
  • Handling API Rate Limits (429 RESOURCE_EXHAUSTED): Engines like Self-Consistency (\(N=5\)) and LLM-as-a-Judge hit rate limits under parallel evaluation. I implemented exponential backoff retries directly in _generate_content_with_retry to maintain benchmark stability.
  • Multimodal Ingestion vs CPU Layout Parsing: PyMuPDF layout parsing handles structured text quickly on CPU. However, for complex multi-column resumes or non-standard fonts, direct PDF byte ingestion to Gemini's visual engine eliminates text extraction artifacts.

8. Architectural Recommendations

Based on empirical benchmark findings, I recommend a tiered production architecture for enterprise document extraction:

  1. Tier 1 Automated Processing (LogProb Delta + Platt Scaling): Run primary extractions through LogProbDeltaEngine with a fitted PlattScalingEngine. This delivers reliable confidence scores in under 5 ms. Extractions with calibrated confidence \(\ge 0.75\) are automatically routed to downstream production systems.
  2. Tier 2 Secondary Verification (Grounding Alignment): Extractions falling below 0.75 are passed to GroundingAlignmentEngine to verify factual claims against raw document text via NLI.
  3. Tier 3 Human-in-the-Loop Audit: Documents that fail Tier 2 verification are flagged as FLAG_FOR_HUMAN_REVIEW, giving recruiters focused, audited queues while automating over 80% of routine processing safely.
